Nash · Picker Lite · FreshMart

Data flow

Where every field comes from, where every outcome goes, and what never leaves the server.

01 — The whole thing in one line

Nash owns the data. OnePick borrows it, shapes it for a picker, and hands the outcome straight back.

There is no database. Nothing is stored between requests. Every screen is a projection of what Nash currently holds, and every action is a write back to Nash. That is not a shortcut — it is the decision that makes the app recoverable, because a closed tab loses nothing.

02 — Read path: three resources become one pick row

An order knows what was bought. The catalog knows what it is. Per-store inventory knows where it is. Rendering a single row of a pick list needs all three, and the join is the single riskiest piece of integration work in the build.

The API key exists only inside the server box. The browser never holds a credential and never talks to Nash.

The join, field by field

order.items[].subItems[]
  .sku          ——————————→  products[].sku
  .quantity                        ↓ .id
  .substitution                    ↓
                          products[].id + storeLocationId
                                   ↓
                          inventory[].location { aisle, bay, shelf }

one PickRow =
  name            from products[].name
  image           from products[].imageUrl
  requestedQuantity from subItems[].quantity
  location        from inventory[].location
  isWeighted      from products[].attributes includes "WEIGHTED"
  substitution    from subItems[].substitution
  # channel is deliberately absent - see 03

Location lives on inventory, not on the order. That is the detail that turns a two-call app into a three-call one, and it is why the adapter exists at all rather than the view fetching what it needs.

03 — Channel enters, and stops at the adapter

Nash has no channel field, so the channel rides in on tags and is normalised the moment it lands. The picker view never receives it.

Channel-blindness is a property of the type, not a rule someone has to remember. A component cannot leak the channel into the pick screen because it is never handed one. The analytics stream keeps it, because comparing fill rate across channels is the entire point of unifying them.

04 — Write path: four outcomes, one shape

Every picker action — picked, short, missing, substituted — converges on a single mapping function and a single write. There is no branch in the transport, only in the mapping.

every outcome, one shape
pickedItems[] {
  requestedQuantity   what the customer asked for
  quantity            what is physically in the tote
  status              picked | partially_picked | not_picked | substituted
  weight              only when the product is WEIGHTED
  scannedBarcode      stretch - scan verification
}

There is no picked: boolean anywhere in this flow. A customer orders 1kg of bananas and the picker weighs 0.94kg — that is neither picked nor not-picked. A boolean makes the most common real case unrepresentable, so the model carries quantities from the start.

Close the tab at step 8 and reopen it: the run resumes, because the outcomes already recorded live in Nash rather than in browser memory. That is the practical payoff of statelessness, and it is worth demonstrating live rather than asserting.

07 — What crosses which boundary

CrossesCarriesNever carries
Nash → serverOrders, products, inventory, customer details—
Server → browserJoined PickRow[], the minimum a picker needs to pickAPI key. Org id. Channel. Raw Nash payloads. Customer detail beyond the name
Browser → serverOutcome, quantity, weight, scanned barcodeAnything Nash-shaped. The browser does not know Nash exists
Server → NashpickedItems[], completion status—

The middle row is the one that matters. The key is server-side only and never prefixed NEXT_PUBLIC_ — that prefix would ship the credential in the browser bundle. It also removes CORS as a possible failure at exactly the wrong moment in a demo.

08 — What is deliberately not in this flow

Not built
A database

Two copies of the truth eventually disagree, silently, and usually mid-demo. Would change my mind: multi-device handoff, or offline durability.

Not built
Dispatch and delivery

Nash already does this better than anything built this afternoon. OnePick hands off at items_pick_complete. Would change my mind: never.

Not built
Route optimisation

Location is displayed, not sequenced. A genuine efficiency lever, and not one of the four requirements.
