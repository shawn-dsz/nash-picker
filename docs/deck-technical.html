Read the API before planning anything

The four scenarios were already four statuses

// the brief                    // Nash, already in the schema
mark items picked        →     picked
partial quantities       →     partially_picked
handle out-of-stock      →     not_picked
substitutions            →     substituted

// and the container for all of it
order.requirements: ["pick_and_pack"]
order.items[].subItems[].substitution{ preference, substituteItems[] }

This is a mapping problem, not a domain design problem. It is also the reason there is no database: the state already has an owner.

02 Architecture and key decisions

One deployable, one boundary, no database

No database, no queue, no cache. A second copy of pick state would need reconciling with Nash forever, and reconciliation bugs are the expensive kind.

02 Architecture and key decisions

One pick row is a three-way join

Every identity mismatch in this join returns HTTP 200 with an empty result, never an error. So a join miss is logged rather than swallowed — an empty aisle column reads as missing data, not as a bug.

02 Architecture and key decisions

The model, and the boolean that is not in it

type PickStatus = "picked" | "partially_picked" | "not_picked" | "substituted";

type Outcome = {
  subItemId: string;  sku: string;  status: PickStatus;
  requestedQuantity: number;
  quantity: number;          // what is physically in the tote
  weight?: number;           // WEIGHTED products only
  substituteSku?: string;    // substituted only
  scannedBarcode?: string;   // what was scanned, never what was expected
  scanOverride?: boolean;    // bypassed a failed or missing scan
};

// one rule, one place. The UI cannot disagree with the write path.
statusFor(requested, got, substituted) → PickStatus

There is no picked: boolean anywhere, deliberately. 0.94kg against a 1kg order is the case a boolean cannot express, and it is the ordinary case in a deli aisle.

02 Architecture and key decisions

The scan gate

A wedge scanner types the digits and sends Enter, so a focused input is the production mechanism, not a stand-in. A phone camera would feed this same resolution path.

02 Architecture and key decisions

Serpentine, over a layout the store owns

Bays sort naturally, so B2 comes before B10 — the bug a plain string sort makes quietly. The gain is measured against the basket as ordered and shown only when it is real: on a small basket it is sometimes zero, and claiming a saving that was not made is worse than reporting none.

02 Architecture and key decisions

Five things the docs do not say

01PATCH replacesitems is replaced, not merged. A partial send silently destroys the rest of the basket and returns 200 either way. So the write reads the order first and sends the whole array
02Two envelope shapes/orders returns {results,totalCount}. /products and /inventory return {<name>,totalResults}
03Summary vs detailGET /orders carries no items and no requirements. And itemsCount is a string, so arithmetic on it concatenates silently
04Append-only ordersCancel and delete are both 404 and status is refused on PATCH. Correct for a fulfilment system, and it means the demo reset supersedes rather than removes
05No pickedItemsPlanned the whole write path against it. It is a response field, not a request one. Probed at 12:30 rather than 14:30, so it cost one function instead of the architecture

03 Tradeoffs

“Metadata is your own database, but worse”

The fair hit
My schema, in someone else's untyped field

No validation, no consumer, and Nash's own systems cannot act on it

What it keeps
One copy of the truth

A second store means owning reconciliation forever. Metadata is a worse container with the same ownership model

The real fix is a first-class picking field on the Nash side. If you built one, this app consumes it in an afternoon, because the mapping is one pure function with eleven tests around it.

03 Tradeoffs

“Shouldn't this be a WebSocket?”

today     browser ──poll──▶ server ──poll──▶ Nash
socket    browser ◀─push─── server ──poll──▶ Nash   ← still polling
correct   browser ◀─push─── server ◀─hook─── Nash   ← nothing polls

A socket moves the poll one hop back. The first thing to build is a webhook subscription, not a transport. And when the transport comes, SSE over WebSocket: the traffic is one-directional and SSE reconnects itself, which matters more than speed in a building that drops signal in the freezer aisle.

What actually needs to be real-time is not new orders. It is two pickers opening the same order, and that is a locking problem, not a transport problem.

04 Current state

What it cannot do, said out loud

01Crash mid-runOutcomes buffer on the device and flush at completion, so a crash in aisle six loses the run. The fix is a write-ahead queue, not a per-tap write
02Two pickers, one orderNo locking and no claim step. A faster refresh narrows the window and never closes it
03Pick durationNothing stamps run start, so elapsed time is not derivable. The speed claim is a design argument and a route measurement, not a timing
04Scan mismatch rateOverrides are recorded so override rate is real. Rejected scans are not counted, so a true mismatch rate still needs a per-line counter
05Stale planogramSequencing on stale aisle data sends a picker confidently to the wrong bay, which is worse than no sequencing because they trust it
