JSON flow

One sub-item, followed end to end. Every payload on this page was captured from the live sandbox, not written by hand.

The item: DRY-PAS-201 Spiral Pasta 500g, on order FM-1003 for Ana Rossi. It is out of stock, and the customer pre-approved penne. That makes it the one row that touches every part of the system.

What is missing

No name a picker would recognise beyond a description, no image, no location, and no idea it is out of stock. The order knows what was bought. It does not know what it is or where it lives.

The join, and why it is fragile

subItems[].sku → products[].sku, then products[].externalIdentifier → inventory[].externalProductId. Four identity hops, and every mismatch returns HTTP 200 with an empty result. Never an error. A broken join renders as a pick row with a blank aisle, which reads as missing data rather than a bug, so the adapter logs a miss instead of swallowing it.

Location and price both live on inventory, not on the product. That is correct modelling, not an inconvenience: where a jar sits and what it costs are per-store facts. It is also the entire reason a third call exists.

03 ADAPTER

Three payloads become one row

lib/adapter.ts → getPickRun() → PickRow

{
  "subItemId": "FM-1003-1",
  "sku": "DRY-PAS-201",
  "name": "Spiral Pasta 500g",          // from products
  "imageUrl": "https://placehold.co/...",  // from products
  "requestedQuantity": 1,                // from the order
  "isWeighted": false,                    // products.attributes
  "weightUnit": null,
  "location": { "aisle": "2", "bay": "B1", "shelf": "2" },  // inventory
  "inStock": false,                       // inventory
  "onHand": 0,
  "barcode": "930000002019",
  "substitution": {
    "preference": "substitute",
    "source": "customer",
    "items": [ { "sku": "DRY-PAS-200",
               "name": "Penne Pasta 500g",   // resolved from the catalog
               "quantity": 1,
               "imageUrl": "https://..." } ]
  }
}

The substitute SKU became a product

Nash returns { sku: "DRY-PAS-200", quantity: 1 }. The adapter reaches back into the catalog it already loaded and turns that into "Penne Pasta 500g" with an image. The picker never sees a SKU string. That is a second use of the same in-memory index, at no extra network cost.

There is no channel field on PickRow. Channel arrives on tags as "channel:uber_eats", is normalised here, and stops. The pick screen is channel-blind by construction rather than by discipline, because it is never handed one.

05 BROWSER

The outcome

lib/outcomes.ts → Outcome

{
  "subItemId": "FM-1003-1",
  "sku": "DRY-PAS-201",
  "status": "substituted",        // one of Nash's four, nothing invented
  "requestedQuantity": 1,
  "quantity": 1,
  "substituteSku": "DRY-PAS-200"
}

// the weighted case, from FM-1002 - 1kg ordered, 0.94kg on the scale
{
  "subItemId": "FM-1002-1",
  "sku": "PRD-BAN-001",
  "status": "partially_picked",   // derived, never passed in
  "requestedQuantity": 1,
  "quantity": 0.94,
  "weight": 0.94
}

There is no boolean anywhere in this object

0.94 against a request of 1 is neither picked nor not-picked. statusFor(requested, got) derives the status from the two numbers in one place, so the screen and the write path cannot disagree about what partial means. A picked: boolean would make the most common case in fresh food unrepresentable.

06 NASH

Back to the system of record

PATCH /v1/order/{id} - server side only

Verified, and not what the plan assumed

pickedItems is not an argument on update, and order status is not writable. Probing the live API found this before the write code was written rather than at 14:30. Outcomes land on subItems[].metadata and the run summary on orderMetadata, both confirmed to persist.

// one PATCH per run, not one per tap
{
  "orderMetadata": {
    "channel": "uber_eats",
    "pick_status": "items_pick_complete",
    "pick_fill_rate": "1.00"
  },
  "items": [ { "subItems": [ {
    "id": "FM-1003-1", "sku": "DRY-PAS-201",
    "metadata": { "pick_status": "substituted",
                  "picked_quantity": "1",
                  "substitute_sku": "DRY-PAS-200" }
  } ] } ]
}

The cost, stated plainly

PATCH on items replaces rather than merges, so the whole items array is sent every time. And because the outcome sits in a general-purpose metadata field, Nash's own systems cannot act on it: completion is a convention this app defines, not a status the platform recognises. Dispatch will not trigger off it. If a first-class picking write path exists, it is one function to switch, which is exactly why the mapping was isolated.

RECAP

Six calls, one row

#WhereWhat it adds
01GET /order/{id}What was bought, and the customer's substitution decision
02aGET /productsName, image, and the WEIGHTED flag
02bGET /inventoryAisle, bay, shelf, price, real stock level
03adapterJoins all three. Resolves the substitute SKU to a product. Drops channel
04-05browserOne decision, one of four statuses, quantities never booleans
06PATCH /order/{id}Outcomes back to the system of record. One call per run

Measured: queue 445ms across five calls, one pick run 210ms across three. Nothing is cached and nothing is stored, because Nash is the system of record and a second copy would only ever be a copy that disagrees.
